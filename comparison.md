# MediaQuote CLI — Сравнительный отчёт

## 1. Описание проекта и цели сравнения

MediaQuote CLI — консольная утилита для поиска, просмотра и управления цитатами из трёх источников: высказывания известных людей, цитаты из фильмов и цитаты из видеоигр.

Проект реализован дважды — с помощью двух разных ИИ-инструментов:
- `claude/` — версия на базе Claude (Anthropic);
- `deepseek/` — версия на базе DeepSeek.

Цель сравнения — оценить, насколько эффективно каждая модель справляется с реализацией одного и того же ТЗ: от архитектуры до рабочего кода с тестами.

**Claude (Anthropic, Claude Sonnet 4.6)** — коммерческая модель, на момент разработки одна из наиболее актуальных версий в линейке Claude. Позиционируется как модель с сильным акцентом на точное следование инструкциям, работу с длинным контекстом и многофайловые проекты.

**DeepSeek** — бесплатная открытая модель от китайской компании DeepSeek. Сильный универсальный инструмент, широко охватывает разные области: код, математику, общие знания. Бесплатность делает его очень доступным вариантом для учебных и личных проектов.

## 2. Методология

### Как велось сравнение

**Этап 1** — совместно с Claude было подготовлено детальное техническое задание (см. [docs/mediaquote_tz.md](docs/mediaquote_tz.md)). ТЗ включало список команд CLI, REST API эндпоинты, стек технологий, структуру проекта и требования к тестированию.

**Этап 2** — готовое ТЗ было передано обеим моделям с одинаковым стартовым промптом:

> Реализуй проект MediaQuote CLI по следующему техническому заданию. Стек: Python, Typer, Rich, httpx, SQLite, FastAPI. Источники данных: ZenQuotes API (внешний), собственный FastAPI сервер с датасетами фильмов и игр. Нужно минимум 7 групп команд CLI. Реализуй поэтапно, начиная с FastAPI сервера, затем CLI.

Важная оговорка: ТЗ составлялось совместно с Claude, что потенциально даёт ему преимущество — модель лучше понимает собственные формулировки и логику документа.

Фиксировались:
- подход к уточнению задачи перед началом реализации;
- сколько итераций потребовалось до рабочего результата;
- какие уточнения пришлось давать;
- качество и структура итогового кода;
- насколько точно модель следовала ТЗ.

### Критерии оценки

- уточнение задачи перед началом реализации;
- следование ТЗ с первой итерации;
- качество и читаемость кода;
- количество итераций до рабочего результата;
- обработка ошибок;
- проактивность — предложения сверх ТЗ;
- работа с данными и датасетами;
- качество документирования.

## 3. Источники данных — история поиска API

До начала разработки были проверены все доступные публичные API для цитат из фильмов и игр:

- `movie-quote-api` на cyclic.app — мёртвый, cyclic.app закрылся в 2024;
- `F4R4N/movie-quote` на Heroku — мёртвый, Heroku убрал бесплатный план в 2022;
- `LukasF7889/moviequoteapi` на Vercel — `DEPLOYMENT_NOT_FOUND`;
- Zyla Celebrity Lines API — живой, но требует карту для триала;
- TMDB API — живой и бесплатный, но не содержит цитат, только метаданные фильмов.

**Вывод:** публичных API с цитатами из фильмов без регистрации не существует. Принято решение реализовать собственный FastAPI сервер — это соответствует Варианту 2 из требований задания.

**Важный момент по датасетам:** Обе модели получили одинаковые файлы — `movie_quotes.txt` (732 цитаты) и `db.json` (20 игровых цитат). Разница в том, как это произошло: Claude сам предложил найти датасет на Kaggle и дал конкретную ссылку — файлы были загружены и переданы ему в рамках того же диалога. DeepSeek этой инициативы не проявил, начал с встроенного мини-датасета из 10 цитат, и передача файлов потребовала отдельного дополнительного запроса — после которого модель переписала значительную часть кода под новые данные. Оба работали с одинаковыми исходными данными, но Claude интегрировал их сразу, DeepSeek — после лишней итерации.

## 4. Поток 1: Claude / `claude`

### Подход к задаче

В отличие от DeepSeek, Claude перед началом реализации задавал уточняющие вопросы: какие именно API проверены, какой формат данных предпочтителен, как должен выглядеть интерактив после показа цитаты. Это замедляло старт, но снижало количество итераций на исправление.

### Итерация 1 — FastAPI сервер

Реализован с первой итерации без уточнений:
- динамическая загрузка датасета из `movie_quotes.txt` (753 цитаты) и `db.json` (20 цитат);
- маппинг персонажей для известных цитат;
- все нужные эндпоинты включая `/quotes/search` и `/quotes/stats`;
- корректная фильтрация и обработка параметров.

**Результат:** принят без правок.

### Итерация 2 — API-клиент

Предложена архитектура с первой итерации:
- фабричная функция `_make()` для единого формата цитаты;
- fallback-датасет при недоступности ZenQuotes;
- `get_random_quote()` как агрегатор всех источников.

**Результат:** принят без дополнительных итераций.

### Итерация 3 — CLI команды

9 групп команд реализованы за одну итерацию. Примечательно: интерактивный диалог после показа случайной цитаты (сохранить? / в избранное? / оценить?) был предложен самой моделью как логичное UX-решение — в ТЗ он явно прописан не был. Модель аргументировала это тем, что пользователь должен сначала увидеть цитату, и только потом принимать решение.

**Результат:** все команды работают, структура соответствует ТЗ.

### Итерация 4 — исправления

Одно уточнение: таблицы в терминале отображались некорректно из-за эмодзи (wide characters). Claude объяснил причину и исправил `formatters.py`.

### Итерация 5 — тесты

Перед написанием тестов Claude уточнил структуру проекта и названия функций в `api_client.py` — это позволило написать тесты с первой итерации без ошибок. Потребовалось одно уточнение: настройка `conftest.py` и исправление импортов после переименования папки (одна ошибка, один промпт — указать на Sources Root). Итого: **70 тестов, все прошли**.

**Итого итераций: 5-6**

## 5. Поток 2: DeepSeek / `deepseek`

### Подход к задаче

DeepSeek сразу начал писать код без уточняющих вопросов. С одной стороны — быстрый старт. С другой — больше итераций на исправление, потому что часть решений не совпадала с ожиданиями из ТЗ.

### Итерация 1 — архитектура

Предложена избыточная архитектура: `core/`, `clients/`, `cache/`, `services/`, `migrations/`, `e2e/` тесты, Alembic, SQLAlchemy. Это оверинжиниринг для учебного проекта. Потребовалось уточнение с явным запретом лишних слоёв.

### Итерация 2 — стек

После уточнения структура стала проще, но модель на первой итерации предложила `click` вместо `typer`. Потребовалось ещё одно уточнение.

### Итерация 3 — FastAPI сервер

Сервер реализован, но:
- поле текста цитаты названо `text` вместо `quote`;
- эндпоинты отличаются от согласованных в ТЗ;
- использован встроенный мини-датасет (10 фильмов, 10 игр) — модель не проявила инициативы по поиску внешних данных, передача готовых файлов потребовала отдельного промпта, после которого пришлось переписывать часть кода.

Потребовалось уточнение по именованию полей.

### Итерация 4 — CLI команды

7 групп команд реализованы, но с конфликтом имён: файл `cli.py` и папка `cli/` в одной директории вызвали ошибки импортов. Потребовалась дополнительная итерация.

### Итерация 5 — импорты и URL

После уточнения импорты исправлены, добавлены `__init__.py`. Дополнительно возникла проблема с URL эндпоинтов — DeepSeek генерировал запросы к `/api/v1/random`, `/api/v1/movies/{title}/quotes` и т.д., тогда как наш сервер отдаёт данные на `/movies/quotes/random`, `/games/quotes/random`. Потребовалось переписать `api_client.py` и добавить метод `_normalize()` для маппинга полей (`character` → `author`, `movie`/`game` → `source`).

Интерактивный диалог после показа цитаты реализован не был — модель ограничилась флагом `--save` без дальнейшего взаимодействия с пользователем.

**Визуально** итоговый вывод DeepSeek выглядит немного чище — более минималистичные панели без лишних элементов. Это субъективное преимущество визуального оформления. Однако Claude использует эмодзи, что делает использование CLI визуально приятнее.

### Итерация 6 — тесты

Тесты написаны DeepSeek, но запустить их сразу не получилось. Потребовалось 3 дополнительных промпта:
- первый — исправить импорты (`cli.api_client` → `api_client`);
- второй — убрать несуществующий атрибут `MEDIAQUOTE_DIR` из patch в `conftest.py`;
- третий — переписать `test_api_client.py` полностью, так как URL в моках (`/api/v1/random`) не совпадали с реальными эндпоинтами сервера (`/movies/quotes/random`), и тест на `get_zen_quote` падал потому что такого метода в `api_client.py` нет.

После всех исправлений: **31 тест, все прошли**.

**Итого итераций: 9-11**

## 6. Советы по промпт-инжинирингу

- Подготовка детального ТЗ до начала разработки значительно сокращает количество итераций.
- Модели которые задают уточняющие вопросы дают более точный результат, хотя стартуют медленнее.
- На дебаге лучше работали промпты с конкретным симптомом: что сломано, где именно, какого поведения ожидаем.
- Явно указывать в промпте не только что делать, но и чего не делать — без SQLAlchemy, без Alembic, без лишних слоёв.
- Проверять доступность внешних API заранее и передавать эту информацию модели.
- Если есть датасеты — сообщать об этом явно, иначе модель придумает собственное минимальное решение.

## 8. Выводы и рекомендации

**Claude** точнее следовал ТЗ, задавал уточняющие вопросы перед стартом, предлагал решения сверх требований (датасет на Kaggle, интерактивный диалог). Код получился чище и потребовал меньше итераций. Как более свежая и специализированная коммерческая модель, Claude показал себя надёжнее именно в многошаговых задачах с чётким ТЗ.

**DeepSeek** быстрее стартует и хорошо исправляет ошибки при конкретных уточнениях, но без явных ограничений склонен к оверинжинирингу. При одинаковом промпте сделал заметно меньше функциональности — рабочий, но минимальный результат. При этом DeepSeek полностью бесплатен, что делает его очень привлекательным вариантом для учебных проектов где бюджет ограничен — за нулевую стоимость результат вполне достойный.

**Контекст сравнения:** Claude является коммерческим продуктом с платной подпиской, DeepSeek — бесплатная открытая модель. С учётом этой разницы результаты DeepSeek выглядят вполне конкурентоспособно: при более детальных промптах и явной передаче всех данных с первого запроса разрыв в качестве заметно сокращается. Для задач где важна доступность и скорость ответа — DeepSeek остаётся сильным выбором.

**Оговорки:** ТЗ составлялось совместно с Claude, что даёт ему преимущество в понимании контекста. Оба получили одинаковые датасеты — разница лишь в том, что Claude запросил их сам в ходе диалога, а DeepSeek потребовал отдельного промпта с передачей файлов и последующей переработки кода.

**Главный вывод:** при работе с любой моделью детальное ТЗ и явные ограничения в промпте критически важны. Коммерческие модели типа Claude показывают преимущество в точности следования инструкциям и проактивности, бесплатные модели типа DeepSeek — в доступности и скорости. Выбор инструмента зависит от задачи и бюджета.

Рекомендации:
- составлять ТЗ до начала генерации кода;
- явно указывать стек, структуру папок и чего не делать;
- передавать все имеющиеся данные (датасеты, примеры API) с первого промпта;
- проверять доступность внешних API заранее;
- раньше подключать тесты.
